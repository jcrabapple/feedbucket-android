## 0. Scope

In scope (D1, D5–D12, D17): standalone no-account local RSS reader on the ReadYou foundation; saved searches, rules, mutes with previews and apply-to-existing; recently read; updated-article snapshots and diffs; durable list/reading positions; bounded durable full-text+image downloads; offline FTS search; OPML; separate full-state FeedBucket migration import; Material 3 Expressive conformance gate.

Out of scope (D1, D13, D14, D15): server/API/AI/podcast/newsletter/social features, new sync services, retiring the live web service, physical-device use, destructive deduplication. Upstream service providers (Fever/Google Reader) are preserved where practical but never onboarding requirements (D1); all S# behavior below is specified for the LOCAL account type.

- Query grammar (`feedbucket/db.py:1047 parse_search`): `shlex.split` with fallback to whitespace split on quoting error; `sort:asc|desc|relevance` tokens (last wins); one `tag:NAME` (last wins, matched lowercased); all remaining tokens are AND-ed terms. `search_filters` (db.py:172) renders each term as `LIKE %term% ESCAPE '\'` over `e.title OR e.summary OR e.content` with `\`, `%`, `_` escaped (`like_term`, db.py:167).
- Listing (`db.py:588 list_entries`): views `unread` (unread join AND `s.muted = 0`), `starred`, `updated` (inner join `updated`, `s.muted = 0`), `recently_read`, `all`; query-mute exclusion (`NOT (feed in scope AND mute terms)`, db.py:652) applies to `unread` and `updated` views only; default order `COALESCE(e.published, e.created_at) DESC, e.id DESC`; `recently_read` orders by `rr.read_at DESC`; `sort:relevance` scores per term title=5, summary=2, content=1, ties by published DESC, id DESC; default limit 500.
- Ingest (`db.py:452 store_entries`, `feedbucket/actions.py`): per-feed single transaction. `external_id = entry.external_id or entry.url or sha256(joined field values)`. New entry: actions applied (`is_update=False`); entry inserted into `unread` only if no matching `mark_read` effect; `star` effect inserts into `starred` under a budget of 100 stars per `store_entries` run (decremented only on actual insert). Existing entry: compared keys `(title,url,author,published)` if `extracted` else `(title,url,author,summary,content,published)`; equal → untouched; changed → snapshot gate (only if `show_updates` AND NOT `extracted` AND `original_content IS NULL` AND published within 7 days (missing published counts as recent; unparseable counts as NOT recent) AND content changed with `abs(len(plain(new)) - len(plain(old))) > 50`) stores the OLD content into `original_content` once; then extracted entries update ONLY `title,url,author,published`, non-extracted update all content fields; `updated` row upserted when `show_updates`; actions re-applied with `is_update=True` where `mark_read` clears `unread` AND `updated`, and `star` is skipped.
- Rule matching (`actions.py entry_matches`): scope = all feeds, or `feed_ids ∪ feeds(tag_ids)` intersected with existing feeds; match = optional `tag:` must be among feed tags (casefold) AND every term `casefold`-substring of `"\n".join(title, summary, content).casefold()`. Note the asymmetry in the WEB implementation: rule matching is Unicode-casefold substring in Python; listing/search uses SQLite LIKE (ASCII case-insensitive); query mutes use LIKE at list time but casefold at ingest time (`actions.py:105–123` has no `action_type` guard). (amended by t_8df74936, R1) This spec NO LONGER preserves that asymmetry: Android unifies all surfaces on the canonical S12a contract, documented as a deliberate improvement.
- Preview/apply (`actions.py preview_action` / `apply_action_to_existing`): preview = count + first 20 rows `(id,title,feed_title,published)`; apply-to-existing runs in one transaction over the full scoped match set and returns the row count; `mark_read` also deletes `updated`.
- Read/star (`db.py:839 set_read`, `:856 toggle_star`, `:1002 mark_all_read`, `:867 clear_recently_read`): mark-read deletes `unread` and `updated`, upserts `recently_read(read_at=now)`; mark-unread re-inserts `unread` and deletes `recently_read`; mark-all-read is scoped to the current listing (view/feed/query/sort) and returns the count.
- Diff (`feedbucket/diff.py build_content_diff`): returns None if original empty or lengths equal; tokenizes SANITIZED html with regex `<[^>]+>|\S+|\s+`; `difflib.SequenceMatcher(autojunk=False)`; wraps removed/added token runs in `<del>`/`<ins>`; sanitizes output; any exception → None (no diff, never an error).
- OPML (`feedbucket/opml.py`): export OPML 2.0, one flat `<outline type="rss">` per feed with `category` = comma-joined tags; import walks NESTED outlines, inheriting and accumulating `category` attrs, requires `xmlUrl`, title = `title || text || feed_url`, order-preserving dedupe, insert via ON CONFLICT DO NOTHING (idempotent).
- URL safety: entry URLs stored only when scheme is http/https (`safe_entry_url`); titles/authors stored as PLAIN TEXT (`plain_entry` strips HTML); summary/content stored as sanitized HTML (nh3).
- Extraction trigger (web): entry considered teaser when stripped text `< max(200, 0.4 × feed median body length)` AND `< 700` chars; re-extraction length guard minimum 120 chars; extraction failures are silent no-ops that never replace existing content (`feedbucket/extract.py`, `db.py:820 feed_median_body_len`).

## 2. Final data shape (Room schema v8) and migration

**S1 — One migration, decided up front.** The FINAL v1 schema is Room version 8, reached by exactly one migration `MIGRATION_7_8` from upstream v7. Feature waves may NOT add columns/tables later in v1; they consume this shape (approved direction step 2: "Define FINAL model composition before features widen it"). Any v1 change to this section requires a spec amendment card, not a silent coder decision.

**S2 — Preserve upstream tables and ids.** `account`, `feed`, `group`, `article`, `archived_article` keep their names and primary keys. `article.id` stays TEXT. Existing rows keep their random UUID-based ids forever; determinism applies to NEW inserts only (S6). `account` is untouched; the standalone product uses exactly one Local account.

**S3 — Denormalize `updated`/`recently_read` onto `article`.** The web uses side tables keyed by entry_id with CASCADE deletes; Android uses `isUpdated`/`contentChangedAt`/`readAt` columns. Observable behavior is identical (queue membership, drain-on-read, ordering by readAt DESC); a column avoids two joins in every paging query and survives Room's identity-hash checking without extra entities. Acceptance tests pin the observable behavior, not the shape.

**S4 — Tags vs groups.** Web feeds carry multiple tags; ReadYou feeds carry one `groupId`. v1 keeps `groupId` as the single navigational folder and adds `feed.tags` (CSV) as the data-layer parity carrier used by `tag:` query tokens, rule `groupIds` scoping (which resolves against BOTH `groupId`-derived group ids and `feed.tags` names, see S13), OPML import (all folder/category names) and migration import (all web tags). UI for editing multiple tags per feed is deferred to the design contract; the data path must be complete in wave B.

**S5 — Migration `MIGRATION_7_8`.** Pure SQL (plus the post-migration Kotlin normalization backfill of step 7), exported schema 8.json committed, no data loss:
1. `ALTER TABLE article ADD COLUMN` for each of §2.1 (defaults as tabled).
2. `ALTER TABLE feed ADD COLUMN` for each of §2.2.
3. `CREATE TABLE` for §2.3 entities (Room-exact DDL from 8.json), `CREATE INDEX` for `article_download.state`, `import_run.state`, `list_position.updatedAt`, `reading_position.updatedAt`, plus FK triggers Room expects.
4. (amended by t_8df74936, R4) FTS: create `article_fts` with Room's EXACT generated external-content DDL from 8.json, then backfill the existing v7 corpus with `INSERT INTO article_fts(article_fts) VALUES('rebuild');` (SQLite external-content FTS4 tables are created EMPTY — sqlite.org/fts3.html §6.2.2). Do NOT hand-write content-sync triggers: Room 2.7.2 owns them (`room_fts_content_sync_*`; verified in `room-compiler-2.7.2.jar` `androidx.room.vo.FtsEntity` constants, and per the `Fts4` KDoc Room "will create the necessary triggers to keep the tables in sync" and removes/re-creates them around migrations). The FTS `docid` maps directly to `article`'s implicit rowid (trigger template `WHERE docid=OLD.rowid`) — a TEXT-PK content entity is a rowid table and needs NO separate mapping table. `Migration7To8Test` verifies sync BEHAVIORALLY (post-migration DAO insert → MATCH finds it; update → index follows; delete → gone) instead of asserting hand-written trigger names.

The S12a `*Lower` columns are added with DEFAULT `''` and are NOT backfilled in SQL (SQLite `lower()` is ASCII-only and would not equal the canonical Kotlin normalization for non-ASCII text) — see step 7.

(amended by t_8df74936, R4) Migration tests (instrumented, `room-testing` MigrationTestHelper): v7 fixture → migrate → assert exact table/column/index set against 8.json, assert fixture row values preserved, assert FTS rebuild round-trip (search a pre-migration v7 article body-only term AFTER migrate) and trigger-driven sync (insert via DAO after migrate → MATCH finds it). The RED state for "missing migration" is a RUNTIME failure, not a compile failure: Room 2.7.2 throws `IllegalStateException("A migration from 7 to 8 was required but not found. Please provide the necessary Migration path via RoomDatabase.Builder.addMigration(Migration ...)")` from `RoomOpenHelper` (verified string in `room-runtime-android-2.7.2.aar`); the plan's Wave B RED check is written against that runtime behavior. Downgrade is unsupported (Room default: crash) — S31 retention/backup story covers restore.

(amended by t_8df74936, R1) Normalization backfill: a one-shot, resumable Kotlin pass runs on first DB open after migration (RoomDatabase callback, off the main thread, batched ≤500 rows/transaction): for every article where a source column is non-empty and its `*Lower` shadow is `''`, recompute via `TextNormalizer`. Self-gating and crash-safe (the emptiness condition IS the resume locator; no meta table needed). Before normalization completes, shadow columns are empty for existing rows, so both ASCII and Unicode searches/rule evaluations over them would miss matches. Gate search and rule evaluation against the affected library until the resumable pass completes; show explicit preparation progress while browsing existing feed content remains available. Acceptance tests pin ASCII and Unicode matches immediately after readiness, parity with a fresh v8 install, and restart recovery without applying rules to a half-normalized library.

### 2.4 IDs and import identity

**S6 — Deterministic ids for new articles.** New inserts (sync, import) use `id = "<accountId>$" + sha256hex(feedUrl + "\n" + externalId)` where `externalId = guid.ifBlank { link }.ifBlank { sha256hex(title|url|author|published|contentFields) }` — the exact web fallback chain (`store_entries`, db.py:496). Rationale: idempotent re-sync, re-import and OPML-then-migration double imports converge on one row; the web already relies on `UNIQUE(feed_id, external_id)`. The `$` spacer convention is preserved so upstream code paths that split on it keep working. Existing UUID rows are NOT rewritten (rewriting PKs would cascade into every consumer for zero user-visible gain); identity resolution for old rows stays `(feedId, link)`.

**S7 — Dedupe on ingest.** An incoming article matches an existing row when `feedId` matches AND (`guid` non-empty AND equals existing `guid`) OR (`link` non-empty AND equals existing `link`). Match → update path (S20a); no match → insert with S6 id. `INSERT` uses `OnConflictStrategy.IGNORE` on the PK as a last-resort race guard (two workers computing the same deterministic id).

**S8 — Import identity map.** Every migration/OPML-created entity records `(source, sourceId, targetKind, targetId)` in `import_identity`. FeedBucket sources use `'feedbucket'` with ids `'entries:<id>'`, `'subscriptions:<id>'`, `'saved_searches:<id>'`, `'actions:<id>'`, `'tags:<name>'`. Re-import consults the map first: mapped rows are SKIPPED for content and counted as `skipped`; state refresh (unread/starred/readAt/isUpdated) for already-mapped articles happens only when the import run is explicitly started in "refresh state" mode from the import UI (default OFF). Rationale: web `import_subscription` is ON CONFLICT DO NOTHING — idempotent, never destructive; D13 forbids destructive dedup.

**S9 — Migration article ids.** Imported FeedBucket entries get the S6 deterministic id computed from `(subscription.feed_url, entry.external_id)`, so importing the same DB copy twice — or importing after already having synced the same feed live — converges on the same row.

## 3. Query & rule grammar (shared across search, previews, ingest, mutes)

**S10 — One parser, one matcher module.** (amended by t_8df74936, R1) Create `domain/model/query/SearchQuery.kt` (parser), `domain/model/query/TextNormalizer.kt` (the SINGLE canonical case-normalization implementation, S12a) and `domain/model/query/QueryMatcher.kt` (in-memory matcher) as the ONLY implementations; search UI, saved searches, rule preview, rule ingest application and mute filtering all consume them, and every DAO write path that touches `title`/`shortDescription`/`rawDescription`/`fullContent` consumes `TextNormalizer` for the shadow columns. No second grammar and no second normalization may exist (D7).

Parser (exact port of `parse_search`, db.py:1047):
- Tokenize POSIX-shell-style: double quotes, single quotes, backslash escapes (a Kotlin port of `shlex.split` semantics; a tokenizer bug here silently changes every feature, so it is unit-tested against Python `shlex` outputs recorded as fixtures). On unbalanced quotes, fall back to plain whitespace split (web `except ValueError: query.split()`).
- `sort:asc|desc|relevance` (case-insensitive value; last valid token wins; invalid value ignored, leaving default).
- `tag:NAME` (NAME must be non-empty; last wins; comparisons lowercase).
- All other tokens are search terms, AND-ed, order preserved.
- Output: `SearchQuery(terms: List<String>, tag: String?, sort: Sort)` — pure data, no SQL.

**S11a — SQL rendering (search/list/mute filtering).** (amended by t_8df74936, R1 — supersedes S11) Each term renders as `(?lowerCol LIKE '%' || :normTerm || '%' ESCAPE '\')` OR-ed across the four normalized shadow columns `titleLower`, `shortLower`, `rawLower`, `fullLower`, terms AND-ed. `:normTerm` = `likeEscape(TextNormalizer.normalize(term))` with `\`, `%`, `_` escaped exactly like `like_term` (db.py:167). Because both sides pass through the SAME normalizer, the SQL path implements the canonical S12a predicate exactly (Unicode case-insensitive substring) — the web's ASCII-only LIKE limitation (db.py:182–184) is a documented, deliberate improvement, not a parity break of any user-visible contract. Rationale for the 4-field set: web matches `title/summary/content` where `content` is the body that extraction REPLACES in place; Android keeps feed body (`rawDescription`) and extraction (`fullContent`) side by side, so matching both reproduces the web observable ("body-only matches work", "extracted content changes search results", D10) without losing pre-extraction text. `tag:` renders as `EXISTS (SELECT 1 FROM feed f2 WHERE f2.id = article.feedId AND (',' || f2.tags || ',' LIKE '%,<tag>,%'))` — CSV-safe containment, lowercase both sides (tags are stored lowercased, S4). Write-path invariant: every INSERT/UPDATE of a source text column recomputes its shadow column IN THE SAME TRANSACTION via `TextNormalizer` (enforced at DAO level; unit test asserts parity for every writer).

**S12a — ONE canonical match contract.** (amended by t_8df74936, R1 — supersedes the two-matcher S12, satisfying D7's "one matching/query model for search, previews and ingest")

- **Normalization**: `TextNormalizer.normalize(s: String?): String = s?.lowercase(Locale.ROOT) ?: ""` — Unicode SIMPLE lowercase, one implementation, used for shadow-column writes (S11a), query-term prep (S11a) and the in-memory `QueryMatcher` alike.
- **Predicate**: a term matches an article iff `normalize(term)` is a substring of `normalize(field)` for ANY of `title`, `shortDescription`, `rawDescription`, `fullContent` (per-field OR; all terms AND-ed). `tag:` matching per S13. This ONE predicate serves search, list views/mute filters, saved searches, rule previews, apply-to-existing and ingest application.
- **Deliberate improvements over web inconsistencies** (recorded, not silent): (a) web search SQL is ASCII-case-insensitive LIKE (db.py:182–184) while web rules use Python `casefold` (actions.py:77–78) — Android unifies both on Unicode lowercase; (b) web query-mutes evaluate via SQL at list time (db.py:652–676) but via casefold at ingest time (actions.py:113) — one rule no longer has two match semantics; (c) web rule matching concatenates fields with `"\n"` (actions.py:77), allowing terms to match across field boundaries — Android's per-field OR removes that false-match class.
- **Deviation from Python `casefold`, pinned by fixtures**: Kotlin `lowercase(Locale.ROOT)` performs simple case mapping, NOT full folding — `ß` does not match `ss`, ligatures (`ﬁ`) do not expand. Chosen because SQLite LIKE offers no full-fold mode, so a full-folding contract could not be implemented identically in SQL and Kotlin. Known limitation, documented in the search grammar help.
- **Mandatory fixtures** (§13 items 1a/2/12): non-ASCII casefold pins — Turkish: `normalize("İ")` = `"i̇"` (U+0069 U+0307), so term `i` matches text containing `İ`; term `i` does NOT match dotless `ı`; Greek: `Σ`→`σ` matches, final `ς` documented as its own char; Cyrillic upper/lower; German: `straße` does NOT match `strasse` (full-fold limitation pin). Body-after-280chars: a term occurring ONLY beyond character 280 of the body must match via `rawLower`/`fullLower` even though the 280-char `shortDescription` (and `shortLower`) lacks it. Unicode + mid-word + ESCAPE (`%`, `_`, `\`) fixtures on the SQL path.
- Regex, boolean-operator and semantic search remain OUT of scope (D7 honesty clause).

**S13 — Rule scope resolution.** Port of `resolve_scope` (actions.py:33): `allFeeds=1` → every feed of the account; else union of `feedIds` and feeds whose `groupId ∈ groupIds` OR whose `tags` CSV contains any group NAME resolved from `groupIds` (web resolves tag_ids → subscription_tags; Android group ids map to names, then to both `groupId` and `tags` per S4), intersected with existing feeds. Empty scope → rule never matches (web `_query_mute_filters` skips empty-scope mutes).

**S14 — Relevance sort.** (amended by t_8df74936, R1) Port of list_entries relevance (db.py:632–642): per term, `CASE WHEN titleLower LIKE … THEN 5 ELSE 0 END + CASE WHEN shortLower LIKE … THEN 2 ELSE 0 END + CASE WHEN rawLower LIKE … OR fullLower LIKE … THEN 1 ELSE 0 END`, summed; `ORDER BY score DESC, date DESC, rowid DESC`. `sort:asc` → `date ASC, rowid ASC`; `sort:desc`/default → `date DESC, rowid DESC`. Web ties on integer `e.id`; Android ties on `rowid` (the implicit rowid of the TEXT-PK table) — same observable: stable insertion-order tiebreak. Matching inside the CASE expressions uses the S12a normalized terms over the shadow columns.

**S15 — Views and mute application.** Flow views: `unread` (isUnread=1 AND feed.muted=0 AND query-mutes excluded), `starred` (isStarred=1; mutes NOT applied; muted feeds included), `updated` (isUpdated=1 AND feed.muted=0 AND query-mutes excluded), `recentlyRead` (readAt NOT NULL, ordered readAt DESC, rowid DESC; mutes NOT applied), `all` (no state filter; mutes NOT applied), plus feed scope, group scope and saved-search scope combinable with any view. This is the exact web matrix (list_entries + `_query_mute_filters` applied only to unread/updated). Feed-scope and group-scope filters AND with the view filter.

**S16 — FTS role.** (amended by t_8df74936, R4) `article_fts` is an accelerator and coverage index, NEVER a semantic authority: the canonical predicate for "article matches query" is S12a (normalized substring). Implementation may use FTS to shortlist candidates only where it cannot change results (e.g. `sort:relevance` ranking prefilter must still re-verify with the S11a LIKE path; if a code path cannot guarantee identical result sets, it must not use FTS). Coverage indicator (D10), ACCOUNT-SCOPED (the FTS docid space spans all accounts; `docid` = `article` implicit rowid per S5 step 4): the search screen shows "index covers N of M articles" where `M = COUNT(*) FROM article WHERE accountId = :id` and `N = COUNT(*) FROM article_fts JOIN article ON article.rowid = article_fts.docid WHERE article.accountId = :id`, plus a stale-sync notice when `account.updateAt` is older than 24 h and a backfill-in-flight notice while the S5 step 7 normalization pass is running. Body-only-match, mid-word-substring (FTS cannot find these; LIKE must), extracted-content-change, deletion and migration search tests are mandatory (D10).

## 4. Rules, saved searches, mutes (D7)

**S17a — Rule effects and ingest application.** (amended by t_8df74936, R1) Effects CSV ⊆ {`mark_read`, `star`}. ONLY rules of `type='standard'` participate in ingest application, previews and apply-to-existing; matching everywhere uses the canonical S12a contract. On new-article insert inside the same DB transaction as the insert (port of store_entries): a matching `mark_read` inserts the article with `isUnread=0`; a matching `star` sets `isStarred=1`, subject to a budget of 100 stars per per-feed refresh run (shared across rules within that run, decremented only on actual flips — exact web semantics; rationale: prevents a bad rule from starring an entire backlog in one sync). On publisher UPDATE (S20a): `mark_read` clears `isUnread` AND `isUpdated`; `star` is skipped entirely (web: `star = not is_update and …`). Rules of type `mute` NEVER have ingest effects; they are pure query-time filters on the `unread`/`updated` views (S15), rendered in SQL via S11a and scoped via S13. **Documented divergence from web**: `actions.py:105–123` applies effects for ALL action rows with no `action_type` guard, so a web mute carrying the default `mark_read` effect also suppresses unread insertion at ingest, and web mutes match with SQL LIKE at list time but Python casefold at ingest time. Android v1 deliberately diverges: mutes are view filters only, which makes them fully reversible (deleting a mute reveals the untouched unread state — D7 "all effects must be reversible") and gives every surface one match semantics.

**S18a — Preview and apply-to-existing with a durable undo ledger.** (amended by t_8df74936, R2 — supersedes the in-memory-10k-ids S18) Rule editor shows a live preview: total match count over the current library plus the first 20 matches `(articleId, title, feed name, date)` (port of `preview_action` cap 20). Apply-to-existing asks for count confirmation FIRST, then runs in ONE transaction over the full scoped match set which (a) writes the before-state ledger `state_apply_run` + `state_apply_before` (`wasUnread`, `wasStarred`, `wasUpdated`, `readAtBefore`, `stateVersionAtApply` per article) and (b) applies `mark_read` (clear isUnread + isUpdated, set readAt=now) and `star` (set isStarred; NO budget on apply-to-existing — web has none), bumping `article.stateVersion` on every touched row; returns the exact affected count for display. Undo (D7-reversible, honest): available for the most recent completed, not-yet-undone apply run; restores each ledgered article's before-state ONLY when its current `stateVersion` equals `stateVersionAtApply`. `stateVersionAtApply` records the POST-apply (bumped) version from the same apply transaction — the value the row holds immediately after effects are written — so only later user edits or later runs change it and are detected; storing the pre-apply version would make every undo skip (Gate A resolution, READINESS-v1.md). Articles changed since the apply are SKIPPED and counted ("Restored N · skipped M (changed after apply)") — never a false Undo. `wasStarred=1` rows are restored to starred: undo NEVER clears pre-existing stars. The ledger is Room-durable, so Undo survives process death within retention. Retention: bounded — on each new apply, prune all but the 10 most recent runs (§12). Star toggles and mark-unread remain individually reversible always. `mark_read` applied at INGEST is reversible via normal mark-unread and is NOT ledgered (bounded blast radius: star budget 100/run; documented, not a silent cut).

Saved searches: persisted `(name, query)` rows, listed in the flow filter bar, executable as scopes (view=all + query, S15), renamable/deletable; duplicate names allowed (web parity, S: saved_search). Creating a saved search captures the current query string verbatim including `sort:`/`tag:` tokens.

## 5. Updated-vs-extracted semantics (D6, D8)

**S19 — Extraction contract.** Extraction (auto via `feed.isFullContent` + ReaderWorker, or manual per-article) writes `fullContent` (sanitized HTML, S30a) and `extractedAt`; it NEVER modifies `rawDescription`, `originalContent`, `isUpdated`, `contentChangedAt`, `isUnread`, `isStarred`, `readAt`. Productivity guard (port of web thresholds): an extraction result is accepted only if its plain-text length ≥ 200 chars OR ≥ 40% of the feed's median stored body length (median computed like `feed_median_body_len` over `rawDescription`/`shortDescription` plain-text lengths of the feed's articles); re-extraction of an already-extracted article additionally requires ≥ 120 plain-text chars. Rejected results leave prior content untouched and record NO success (D6: a failed extraction never claims success). Bot/challenge rejection: if the fetched document's `<title>` or first 500 chars match known challenge markers (Cloudflare/"Just a moment"/"Access Denied"/captcha iframes) OR the productive-text ratio is < 5% of document size, treat as failure. Failures are isolated per article (web rescue-everything; upstream `runCatching`), surfaced in UI as a transient "extraction unavailable" state on the article only — never a dialog, never a crash, never content replacement.
**S20a — Refresh update detection (port of store_entries).** (amended by t_8df74936, R7 — supersedes S20) On sync, for an existing match (S7): compute old/new compare keys — extracted (`fullContent != null`): `(title, link, author, publishedAt)`; else `(title, link, author, shortDescription-source, rawDescription, publishedAt)`. `publishedAt` (never `date`) carries publisher-date identity: upstream re-mints `date` from sync time for dateless entries (`RssHelper.kt:223–225`: `date = (publishedDate ?: updatedDate)?.takeIf { !it.isFuture(preDate) } ?: preDate`), so a `date`-based key would flag every refresh of every dateless article as "changed" — fake updates, snapshot churn, updated-queue spam. Date handling: at INSERT `date = publishedAt ?: syncTimeAtInsert`; at UPDATE, `date` is recomputed ONLY when the feed supplies a NEW non-null `publishedAt` — for `publishedAt == NULL` rows the stored `date` is frozen (no manufactured freshness). Equal compare keys → row untouched (no `updateAt` bump). Changed → snapshot gate: if `feed.showUpdates` AND NOT extracted AND `originalContent IS NULL` AND recency holds AND significance holds (plain-text length delta > 50 chars AND content actually differs) → `originalContent = OLD rawDescription` (once, first version only, never overwritten). Recency (web-exact, `db.py:526–537`): `publishedAt == NULL → recent = TRUE` (web assigns `recent = True` and only overrides it inside `if existing["published"] is not None` — missing published counts as recent); `publishedAt != NULL → recent = publishedAt within 7 days of now` (future dates are already mapped to NULL by the upstream future-guard, matching web where a future date trivially satisfies `>= now - 7d`). **Bounded deviation**: web's `ValueError → recent=False` branch (present-but-unparseable date string) is UNREACHABLE on Android because Rome surfaces unparseable dates as null, i.e. invalid ≡ missing → recent; recorded here and pinned by an `UpdateDetectionTest` note, not silently dropped. Then: extracted → update only `title, link, author, publishedAt(+date when publishedAt changed)`; else → update `title, link, author, rawDescription, shortDescription, img, publishedAt(+date when changed)` and their `*Lower` shadows (S11a). If `feed.showUpdates`: `isUpdated = 1`, `contentChangedAt = now`. Then S17a update-effects. `updateAt = now` always on a changed row. Rationale for every threshold: exact web parity (7-day recency db.py:535, >50 significance db.py:538–541, first-version-only db.py:526).
**S21a — Updated queue drain and ordering.** (amended by t_8df74936, R7) Mark-read (single, on-open, or scoped mark-all-read) sets `isUpdated = 0` in the same write (web deletes the `updated` row in set_read/mark_all_read). Opening an article does NOT silently clear `isUpdated` unless mark-read-on-open (S23) fires. The `updated` view shows exactly `isUpdated=1` rows ordered by the DEFAULT scope order `date DESC, rowid DESC` — web parity: `list_entries(view='updated')` only adds the join and keeps the default `COALESCE(e.published, e.created_at) DESC, e.id DESC` order (`db.py:603–605, 627`); it never orders by `updated_at`. S15 is the SINGLE ordering authority (default `date DESC, rowid DESC`; `sort:asc`; `sort:relevance` per S14; `recentlyRead` per S15). `contentChangedAt` is provenance/badge data and is NEVER a sort key (D8: publisher updates stay separate from display ordering).
**S22 — Diff rendering.** "View changes" computes a word-level diff between sanitized `originalContent` and sanitized current `rawDescription` using the web tokenization (`<[^>]+>|\S+|\s+`) and a longest-common-subsequence differ (java-diff-utils 4.x, Apache-2.0 — new dependency, isolated to the diff module); no diff when `originalContent` is null/blank or token sequences are equal (web returns None on equal LENGTH; Android compares token lists, a strict improvement pinned by test: equal-length-but-different text must still diff). Rendered as Compose annotated text (NOT WebView): deletions struck-through with `deleted` semantics, insertions underlined with `inserted` semantics, TalkBack announces "deleted:"/"inserted:" runs, colors meet AA in light/dark and never rely on color alone (strikethrough/underline are the redundant channel). Diff computation failures → feature silently unavailable for that article (web exception→None parity).

## 6. List scope, position and read lifecycle (D5)

**S23 — Mark-read-on-open.** Default ON (web `mark_read_on_open` default ON): opening an article sets `isUnread=0`, `readAt=now`, `isUpdated=0` (S21a) in one transaction, bumping `stateVersion` (S18a). `MarkAsReadOnScrollPreference` stays available, default OFF (D5). Manual mark-unread clears `readAt` (web set_read(False) parity).
**S24a — Durable list positions.** (amended by t_8df74936, R8 — supersedes the delimiter-concat S24 key) Canonical scope key: `scopeKey = "v1/" + [view, feedId ?: "", groupId ?: "", savedSearchId ?: "", query, sort].joinToString("/") { pctEncode(it) }`, where `pctEncode` percent-encodes every byte outside RFC 3986 unreserved (`A–Z a–z 0–9 - . _ ~`). The encoding is injective, so queries containing `/`, `%`, `|`, `-`, Unicode or empty strings can NEVER collide with slot structure (the old `|`-joined `-`-placeholder form was not injective: a literal `-` value was indistinguishable from an empty slot and `|` could appear inside `query`). The `v1/` prefix versions the serialization. On scroll-idle (debounced 300 ms) and on `ON_PAUSE`/navigation-away, persist `(anchorArticleId, anchorItemIndex, anchorOffsetPx)` for the active scope to `list_position`. Restore order: exact anchorArticleId if still in scope → else anchorItemIndex clamped to list size → else top. Restoration happens after process death, after theme/locale change and after back-navigation. Retention: rows older than 30 days pruned on app start (bounded table, no user-visible effect). Exact-restore tests mandatory: collision pairs (empty vs `-` slot values; query containing the delimiter) produce DIFFERENT keys; encode→decode round-trip equality; Unicode query restore.
**S25a — Sticky scope via list generations & neighbors (mark-read must not break prev/next).** (amended by t_8df74936, R8 — supersedes the "does NOT re-query" phrasing, which over-blocked legitimate incoming content) The visible flow list for a scope is a GENERATION (a Paging snapshot anchored at scope entry or last refresh). Contract: (1) writes that change `isUnread`/`isStarred`/`isUpdated`/`readAt` of articles ALREADY in the current generation update those items IN PLACE (badge/weight per design contract) and must NOT remove, reorder or invalidate the generation — a marked-read article remains visible (badged read) until the user changes scope, refreshes, or restarts the app; Paging invalidation triggered by read-state writes is therefore suppressed (implementation detail owned by Wave C; the contract is pinned by tests). (2) Sync completion or explicit user refresh rolls to a NEW generation, which MAY legitimately include newly arrived articles — sticky membership never blocks incoming content. (ReadYou's live Paging invalidation is the KNOWN regression source, W0-cited issues 1091/1271/1240/1285 are demand leads only — the behavior contract here stands on its own.) Prev/next in the reading pager resolves over the CURRENT scope's ordering (S14/S15) with a position fallback ported from web `db.neighbors` (db.py:678): when the current article no longer satisfies the scope predicate (e.g. just marked read in an unread scope), neighbors are found by sort-position comparison — previous = max row with `(sortKey, rowid) < (current.sortKey, current.rowid)` in scope order, next = min row with `>` — using SQL row-value comparison, so navigation survives the article leaving the scope. Mark-all-read is scoped to the current list scope (view/feed/group/saved-search/query/sort) and reports the exact count (web mark_all_read parity); confirmation default ON (web `mark_as_read_confirmation` default 1).
**S26 — Reading position.** Per-article scroll position (`scrollRatioPx`, `contentHeightPx`) persisted on pause/scroll-idle and restored on reopen, including after process death. Reading pager index (which article of the scope is open) is part of `list_position.anchorArticleId`. Positions are best-effort UI state: a restore that lands within ±1 screen of the truth passes acceptance; missing/corrupt rows fall back to top-of-article, never a crash.

## 7. Durable downloads & offline (D9)

**S27a — Download store.** (amended by t_8df74936, R5) Explicit user action "Download" per article (and bulk "download all in scope" capped per S28) enqueues `article_download(state='pending')` + WorkManager one-time work chained after current sync. A download = sanitized self-contained HTML of the article body (`fullContent ?: rawDescription`, rewritten so every `<img src>` in the allowed set points at a local `download_asset` path under the S30a asset origin) + images fetched under caps. Storage location: `filesDir/downloads/<accountId>/<sha256(articleId)>/` (`index.html`, `assets/`, `manifest.json`) — internal files dir, NOT cacheDir: survives cache-clear, survives process death, excluded from auto-eviction (D9). **Readiness model (coherent, replaces the old ready-before-images/atomic-at-completion contradiction)**: everything is written into a sibling staging dir `<sha256(articleId)>.staging/`; `manifest.json` (`{"schemaVersion":1, "textComplete":true, "assets":[{url,path,bytes,sha256}], "assetsComplete":bool, "expectedImageCount":n}`) is written LAST inside staging; the commit is a single atomic directory rename, and only after that rename succeeds does the row flip `pending/downloading → ready`. `ready` therefore ALWAYS means text durably committed with a valid manifest. Images may still be in flight: `expectedImageCount` is recorded at text-commit; each asset landing rewrites the manifest atomically (`manifest.tmp` → rename), bumps `imageCount`/`imageBytes`, and the row's `assetsComplete` flips to 1 when the manifest asset set is FINAL (no more in-flight/fetchable assets — all fetched, or terminally skipped under caps/errors). `assetsComplete=1` alone never claims full images: the **Saved** state additionally requires every expected image landed (`imageCount == expectedImageCount` and zero terminal asset failures). If any asset was terminally skipped/failed (caps/errors), the row stays visibly incomplete — `Text saved · images incomplete N/M` — with manual **Retry images** available even though `assetsComplete=1`; Retry images re-opens the missing set (resets the row so `assetsComplete` leaves 1 while fetching) (Gate A resolution, READINESS-v1.md). UI granularity (D9 "text/image readiness"): `ready && !assetsComplete` → "Text saved · images N/M"; `ready && assetsComplete` → "Saved"; a partially-imaged ready article renders offline with missing-image placeholders. States: `pending → downloading → ready(+assetsComplete) | failed(errorCause, attempts)`; user actions: retry (always available on failed, resets attempts), remove (deletes row + files incl. staging). Recovery: on app start, orphan `downloading` rows with no live work reset to `pending` and re-enqueue once; orphan `*.staging/` dirs are garbage-collected; a `ready` row whose manifest fails schema validation is demoted to `failed(storage)` (never rendered from a corrupt dir).
Failure causes (stable enum strings, surfaced as human text): `network` (DNS/TLS/timeout/connection), `http_4xx`, `http_5xx`, `challenge` (bot wall detected, S19 markers), `oversize` (cap exceeded → text still stored if under text cap, images skipped), `storage` (insufficient space), `cancelled`, `unknown`. D6 applies: a failed download never claims success and never corrupts existing content — download writes are staged to a temp dir and moved atomically on completion.

| Auto retries | (amended by t_8df74936, R6 — S28a) max 3 automatic retries per download, enforced IN THE WORKER (`runAttemptCount >= 3` → terminal `failed(network)`; else `Result.retry()`), with `setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, SECONDS)`. Verified WorkManager 2.10.1 semantics (bytecode, work-runtime-2.10.1.aar): exponential delay = `initialDelay × 2^(runAttemptCount-1)` (`Math.scalb`), linear = `initialDelay × runAttemptCount`, both clamped to [10 s, 5 h] — there is NO ×5 multiplier and no minute-scale default, so the old "1/5/25 min, WorkManager defaults" claim is WITHDRAWN. Manual retry always allowed and resets the counter. | transient network recovery within platform-supported semantics |

Bulk and background-chained downloads gate on `NetworkType.UNMETERED` (+ charging per `account.syncOnlyOnWiFi`/`syncOnlyWhenCharging` for chained work, D12). **S29 — Retention & storage management.** Downloads persist until removed by the user, by article deletion (FK CASCADE + file cleanup hook), or by "Remove all downloads" in Settings → Downloads (with count confirmation). Removing an article that has a download deletes its files in the same user action. `archived_article`/`keepArchived` upstream behavior unchanged. No time-based expiry in v1 (rationale: D9 "durable"; retention rules = user-controlled management, not silent TTL).

## 9. Migration from FeedBucket & OPML (D11)

**S30a — Sanitization and the hardened local render origin.** (amended by t_8df74936, R5) All stored HTML (feed-supplied `rawDescription`, extracted `fullContent`, snapshots `originalContent`, diff output, downloaded `index.html`) is sanitized at WRITE time with Jsoup `Safelist.relaxed()` extended to allow `class` attributes and `http/https/mailto` protocols only; `<script>`, event-handler attributes, `javascript:`/`data:`/`file:` URIs are stripped (D16). **Downloaded-content renderer (distinct hardened configuration)**: the upstream reading pipeline currently runs `javaScriptEnabled = true` with a JavascriptInterface image-click bridge and conditional `allowFileAccess = true` (`WebViewLayout.kt:36,42–54`, verified 2026-11-16) — the downloaded-article render path MUST NOT reuse that configuration. It runs: `javaScriptEnabled=false`, `domStorageEnabled=false`, `allowFileAccess=false`, `allowContentAccess=false`, `allowFileAccessFromFileURLs=false`, `allowUniversalAccessFromFileURLs=false`, no JavascriptInterface. Local assets are served through `androidx.webkit.WebViewAssetLoader` (webkit ≥1.11; 1.18.0 verified in cache) with an `InternalStoragePathHandler` rooted at `filesDir/downloads/<accountId>/<sha256(articleId)>/` under the virtual origin `https://appassets.androidplatform.net/` — file exposure is restricted to ONE local renderer origin instead of a blanket file-access toggle. `shouldInterceptRequest` on this path delegates ONLY to the asset loader; every non-appassets request returns an empty `WebResourceResponse` (blocked — note the upstream client performs raw `HttpURLConnection` fetches in `shouldInterceptRequest`, `WebViewClient.kt:44–53`, which must be unreachable here); link taps route to the external-browser intent, never in-view navigation. Acceptance tests assert the WebSettings values AND run a scheme-block test feeding `javascript:`, `data:`, `file:`, `intent:`, `content:` URIs, asserting non-load and non-navigation ON THE ACTUAL WEBVIEW REQUEST PATH (see §13 item 14; an OkHttp-interceptor-only assertion is NOT sufficient evidence). The JS image-click bridge does not run offline; image interaction on downloaded articles degrades to the native renderer or no-zoom (designer owns the UX; D16 safety wins). Hardening the ONLINE reading pipeline beyond write-time sanitization is recorded as a future candidate, out of v1 scope.

**S31 — Backup & privacy.** (amended by t_8df74936, R3) Room DB + downloads live in internal storage; Android auto-backup posture: DB excluded from cloud backup in v1 (`allowBackup` decision belongs to foundation; spec requires: no secrets and no article corpus leave the device by default, D16). No telemetry (D16). The web `users` table (password_hash, starred_token) is NEVER read by the importer and never present in the v1 export package (S32a). Migration source copies live in `filesDir/imports/` (durable, required for resume) and are purged at terminal state per S32a — NOT the app cache (the old cache-purge story left no resume locator); preview dumps never persist to disk. Developer-side test fixtures are synthetic only (D16). Private local artifacts (`docs/research/logs/`, keystores, `keystore.properties`, `.plan/`, any `*.db` copies) are gitignored — foundation wave adds the ignore entries and a CI check that no `*.db`/keystore file is tracked.

**S32a — FeedBucket migration import.** (amended by t_8df74936, R3 — supersedes S32) Input (preferred): a VERSIONED, SECRET-FREE export package `feedbucket-export-v1.sqlite` produced by `scripts/export_feedbucket_package.py` — a tool versioned in THIS repo (OUTSIDE the live web repo, which stays read-only per D14). The tool: opens the source DB read-only (`file:...?mode=ro` URI + `PRAGMA query_only=ON`; the live service DB is never written), snapshots via the SQLite Online Backup API to a temp file, and writes a new SQLite package containing ONLY the allowlisted tables `subscriptions, entries, unread, starred, updated, recently_read, tags, subscription_tags, saved_searches, actions` (+ optional `user_prefs`) copied via explicit column lists — `users` is never opened or referenced — plus `package_meta(schemaVersion=1, createdAt, sourceSha256, per-table counts)`. Output gates: `PRAGMA integrity_check`; allowlist assertion (no table/column outside the list); secret scan (no `password_hash`/`starred_token` column names anywhere; no value matching a session-token shape). This makes D11's "never export login/session secrets" true of the ARTIFACT, not merely of the importer's query list. Input (compat): a raw user-made SQLite copy (`.backup`) is still accepted — the in-app allowlist + secret guard below apply to both paths. In-app pipeline:
1. Copy the picked file to `filesDir/imports/<runId>.db` (DURABLE — not cacheDir; SAF grants can lapse, and resume needs a stable locator), record `import_run.sourceUri` + `sourcePath`; fingerprint (sha256) + open the retained copy read-only; schema check: `package_meta.schemaVersion == 1` for packages (unknown version → precise rejection), required tables/columns exist (`subscriptions`, `entries`, `unread`, `starred`, `updated`, `recently_read`, `tags`, `subscription_tags`, `saved_searches`, `actions`; `user_prefs` optional). Unknown/missing → import rejected with a precise message, nothing written, retained copy purged.
2. Secret guard (compat path): the importer's column allowlist excludes `users.*` entirely; a test asserts the strings `password_hash` and `starred_token` appear in NO query the importer issues (query-log assertion) and that no imported value matches a session-token shape.
3. Preview phase (no writes): counts table — subscriptions, tags, entries, unread, starred, updated-queue, recently-read, saved searches, standard actions, mute actions, entries with snapshots, extracted entries — plus first 10 subscription titles. Shown to the user with Import/Cancel. The file fingerprint at preview time is recorded.
4. Apply phase: re-fingerprint the retained copy — MISMATCH vs the preview fingerprint → abort, nothing written (preview and apply must consume identical bytes). `import_run(kind='feedbucket', state='running')`; iterate feeds in `subscriptions.id` order; per feed ONE Room transaction creating the feed (S6-style deterministic feed id = `"<accountId>$" + sha256hex("feed\n"+feed_url)`; groups from tags: first tag → group, all tags → `feed.tags` CSV), its entries (ids per S9; `isUnread` from `unread`; `isStarred` from `starred`; `readAt` from `recently_read`; `isUpdated`/`contentChangedAt` from `updated`; `originalContent` from `original_content`; `fullContent`+`extractedAt` from `content` where `extracted=1`, with `rawDescription = original_content ?: summary-as-body fallback (content)` — documented deviation, pinned by fixture test; `*Lower` shadows computed via TextNormalizer at write), saved searches and action rules (web `tag_ids` resolve against imported tag names → Android group ids). Then per-entry `import_identity` rows WITH `createdByRunId` (set only when this run created the row; identity-map skip hits record NULL) and `stateStamp` (article: current `stateVersion`; feed/saved_search/action_rule: sha256 of user-editable content fields). Commit per feed.
5. Counts ledger: `imported`, `skipped` (identity-map hits), `failed` (per-row errors, itemized) written to `import_run.countsJson`; success screen shows the exact ledger. A row-level failure never aborts the feed transaction unless it is a schema/constraint error (then the feed chunk rolls back, counted in `failed`, import continues with the next feed — bounded blast radius).
6. Restart/resume: app start finds `import_run(state='running')` → resume mode against the RETAINED `sourcePath` copy: continue from the first feed lacking identity-map coverage; already-imported feeds count as `skipped`. User-visible: import is resumable, never duplicated (S8), never silently half-applied without a ledger.
7. Rollback & removal: "Cancel" before apply → nothing written, retained copy purged. Failure mid-apply → completed feed chunks REMAIN (each was transactional and identity-mapped) and the ledger says so; a "Retry import" resumes. "Remove imported data" on the result screen deletes ONLY rows with `import_identity.createdByRunId = <this run>` AND a `stateStamp` still matching the current row (articles: unchanged `stateVersion`; feeds/searches/rules: recomputed content hash equal) — pre-existing matched rows and records EDITED SINCE IMPORT are never deleted; skips are counted and reported honestly ("Removed N · skipped M (edited after import)"). Rows created by the run that the user has since edited are skipped, not reverted (D13 non-destructive). Feed deletion carries an extra guard: a feed created by this run may only be removed if deleting it would NOT FK-cascade any retained article (pre-existing, newly imported by another run, or edited-since-import); otherwise that feed's removal is blocked and counted in the skip report ("retained to protect other articles"). Per-row `stateStamp` checks alone cannot protect this graph; the check walks the FK relationship before deletion (Gate A resolution, READINESS-v1.md).
8. Source retention: the `filesDir/imports/<runId>.db` copy is deleted when the user leaves the result surface AND the run is no longer resumable — `completed` successfully or `cancelled` before apply. FAILED runs RETAIN the copy while Retry/Resume is offered, including after leaving the Failed Result screen (resume needs the stable locator; per UI-CONTRACT §6.10 the copy survives until explicit user discard or a later success/cancel). Orphaned copies older than 7 days are GC'd on app start. Retained copies are gitignored, device-internal, never uploaded (D16). (Gate A resolution, READINESS-v1.md)
**S33 — OPML.** Export: OPML 2.0 flat outlines with `category` = `feed.tags` (web export parity) AND folder nesting from `groupId` (ReadYou parity) — both consumers round-trip. Import: existing `OpmlService` path extended: nested folders → group from first folder level, all folder/category names → `tags` CSV (web walk parity), `htmlUrl` → `siteUrl`, duplicate `xmlUrl` → skip with count (ON CONFLICT DO NOTHING parity), report imported/skipped counts. ## 14. Observable state tables (condensed; full offline table in §8)

Sync: `idle | syncing(progress n/m feeds) | success(updateAt bump) | partial(per-feed errors logged, others committed) | failed-all(retry available) | offline-banner`. Extraction: `idle | fetching | stored(fullContent,extractedAt) | rejected-unproductive(no state change) | failed(isolated, transient badge)`. Download: S27a machine (`pending | downloading | ready(±assetsComplete) | failed`) + `waiting-for-wifi` (pending under constraints, S28a). Import: `pick → retaining(durable copy) → validating(schema/package version) → preview(counts+fingerprint) → applying(run ledger, resumable) → completed(ledger) | failed(chunk ledger) | cancelled(nothing written)`. Rule apply: `preview(count,20 samples) → confirm(count) → applying(tx + undo ledger) → done(count, durable Undo per S18a) | error(no partial state)`. Positions: `active-scope persisted | restored-exact | restored-clamped | fallback-top`.

## 15. Amendment process

Changes to S# decisions require a spec-amendment commit on `feedbucket-native` referencing the requesting card, before any coder implements the change. Silent divergence is a review-blocking defect.
