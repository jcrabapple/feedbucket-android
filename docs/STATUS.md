## Post-v1 follow-up: restart deep-composition restore (t_d230c9cf, 2026-11-17)

VERDICT: no code change. Durable cold-start-into-reader after `am force-stop` is NOT contract-consistent; the v1 WARN conflated two distinct kill paths. Documented with emulator evidence (cp_api26, witnesses `build/recon/restart-followup/*.png`):

- Force-stop semantics (the WARN path): `am force-stop` discards the activity record AND its saved-state bundle by design (user/system explicit kill). Relaunch cold-starts at the configured initial root (`MainActivity` startDestination from `InitialPagePreference`, default Feeds). This matches upstream ReadYou and platform convention; no SPEC-v1/UI-CONTRACT-v1 section requires landing inside the reader after force-stop. UI-CONTRACT §2.3(8) pins the Back hierarchy from roots, not the cold-start destination; SPEC §14 positions table covers anchor/scroll restoration within scopes, not navigation restore.
- Genuine process death (state saved, platform-supported): the back stack is already saveable — `rememberNavBackStack` (navigation3-runtime-android 1.0.0, verified bytecode: `rememberSerializable` -> saved-state registry) plus the per-root `RootStacksSaver` and `Route.Reading.Saver`. Verified on emulator with the canonical `always_finish_activities=1` surrogate: Feeds -> feed scope list -> article reader open on "restart probe alpha", Home (activity destroyed with saved state), relaunch -> FULL deep composition restored, reader reopened at the same article (scenarioA PNG). This is the restore path SPEC S24a/S26/UI-CONTRACT §2.2 "saved state" rely on; it works end-to-end.
- Force-stop path (scenarioB PNG): relaunch lands at Feeds root; durable reading state intact (feed rows, unread count 1 — probe alpha read via mark-read-on-open surviving the kill, probe beta still unread); re-entering the feed scope restores the S24a anchor and S26 reading position from the durable `list_position`/`reading_position` tables (pinned by `PositionPersistenceTest`, incl. restore-after-state-clear surrogate).
- A durable start-destination override (persist navigation state to DataStore and rebuild the back stack at cold start) would be a NEW product behavior for an explicit-kill scenario, i.e. a feature decision outside this card's "NO new feature decisions" scope; per minimal-change discipline and SPEC-v1 §15 (design decisions belong to the contract), it was not built. If desired, it needs a spec-amendment card, not a silent coder change.
- Honest residual: on a real low-memory kill of a FOREGROUND activity the platform may also deliver no saved state (no onStop ran); in that case behavior equals force-stop (root restart with durable positions). Saved-state delivery is platform-owned in all cases; the app restores everything the platform hands back.
