# FeedBucket Android — IMPLEMENTATION v1 (serial-wave plan)

> **For Hermes:** Execute wave-by-wave with one coder card per wave on board `feedbucket-android`. Each wave ends with `kanban_request_review(reviewer='reviewer')`. The orchestrator creates the NEXT wave card only after the previous wave is reviewed AND independently integrated (merged, gate re-run by the checkpoint owner). Implementation cards are classic (non-goal). Authority: `docs/APPROVED-DIRECTION.md` (D1–D17) > `docs/SPEC-v1.md` (S#) > this plan. Cite `S#`/`D#` in every card body; cards must not re-decide them.

**Goal:** Ship a standalone, no-account native Android RSS reader (FeedBucket, `us.snakepit.feedbucket`) on the ReadYou foundation that ports the FeedBucket web reader's real semantics — saved searches/rules/mutes with previews and apply-to-existing, recently read, update diffs, durable positions/read state, bounded durable downloads, offline FTS-assisted search, OPML and full-state migration — under a current Material 3 Expressive design gate (D17).

**Architecture:** Single `:app` module (upstream layout kept; namespace stays `me.ash.reader` per D2/S34). Room v7 → one-shot v8 (S1–S5) adds identity/guid, snapshot/update, read/position, download, rule/saved-search, FTS and import-ledger tables. One shared query grammar module feeds search UI, saved searches, rule preview, ingest rules and mute filters (S10–S16). Sync keeps the upstream LocalRssService pipeline; update-detection and rule-application are inserted into its per-feed transaction path (S17, S20). Downloads live in `filesDir` (durable, S27), extraction cache stays where upstream has it. UI is Compose/Material3 ≥1.4.0 stable with the D17/S37 conformance matrix enforced from Gate A onward.

## Scope gates & anti-patterns (all waves, verbatim into cards)

- No whole-repo format/lint-fix sweeps; only owned files. No `@Suppress`, no lint baselines, no `abortOnError` changes, no test deletion/weakening/rewriting-to-pass, no fabricated gates or quoted-from-memory numbers, no silent feature drops (every S# in a wave's section is either implemented with tests or explicitly flagged blocked on the review card).
- REDCHECK per behavior-carrying change: mutate production code to break the behavior, show the test red, restore, show green; record the triple (mutation, red output line, green output line) in the review handoff metadata.
- Dependency additions: license + version check recorded (S36); no network-calling code in tests except MockWebServer/interceptor seams.
- Any discovered need to change an S# decision → stop, comment on the card, orchestrator runs the SPEC-v1 §15 amendment process before code proceeds.
- Wave cards are created serially by the orchestrator AFTER the previous wave's review approval AND independent integration (push + CI green at that commit). Reviewer never edits source; fixes go back to the coder via `request_changes`.
