## 0. Scope

IN scope: adaptive teaser detection with a per-feed median estimate; a single extraction pipeline shared by AUTO (on open), MANUAL (reader action, incl. re-extract) and PREFETCH (existing per-feed `isFullContent` contract at sync); extraction storage in the Room `article` row; ported cleanup rules; quality guards (length, bot-challenge, sanitizer); fetch safety (public-IP/redirect guard, bounded timeouts, bounded response size); a global auto-extract setting (default ON); a silent no-op failure model everywhere.

OUT of scope (binding, per the orchestrator decision in `docs/research/FULL-CONTENT-FETCHER.md`): paywall circumvention of any kind — no unwall/Periscope/Ladder/12ft-style proxy integration, no crawler/search-engine User-Agent spoofing, no archive-snapshot substitution, no client-side paywall-overlay stripping, no AMP/JSON-LD alternate-version fetching. Extraction fetches only the article's own publisher URL with the app's existing User-Agent (E18). Genuinely paywalled sources are handled honestly: feed content as-is plus the existing "View original" path. Also out of scope: per-feed adaptive opt-out UI (deferred, E20), any change to the TLS trust posture (E18 note), and any new third-party dependency (IMPLEMENTATION-EXTRACT §S36/S37 posture).

## 2. Decisions

### Architecture & storage

**E1 — No paywall circumvention (restated, binding).** No proxy service, no crawler-UA spoofing, no archive substitution, no overlay stripping, no AMP/JSON-LD alternates (scope §0). The fetch uses the app's existing `UserAgentInterceptor` UA unchanged (E18). Any future proposal to add such a path requires a new orchestrator-level decision; coders must treat this E1 as a hard wall.

**E2 — One extraction pipeline: `ExtractCoordinator`.** Create `domain/service/ExtractCoordinator.kt` — the single mirror of web `_run_extraction`. Every extraction (AUTO on open, MANUAL extract, MANUAL re-extract, PREFETCH for `isFullContent` feeds) goes through ONE `extract(article, feed, mode)` entry with `mode ∈ {AUTO, MANUAL, RE_EXTRACT, PREFETCH}`; the mode only selects the guard set (E16) and the caller's UX contract (E10/E12). No second fetch-and-parse path may exist: `RssHelper.parseFullContent` and `ReaderCacheHelper`'s fetch internals are retired (E3, E9). Pipeline order (fixed): link check → SSRF/redirect guard (E17) → bounded fetch (E18) → challenge check (E16) → Readability4J parse (E14) → deterministic post-cleaner (E15) → length/productivity guard (E16) → sanitize (E19) → size cap (E16) → single DAO write (E4). Every failure branch returns a typed `ExtractOutcome.Failure(reason)` WITHOUT any DB write — silent no-op (E21).

**E3 — Canonical storage is the Room `article` row; the disk cache is retired.** Extraction results live in `article.fullContent` (sanitized HTML) + `article.extractedAt` (epoch of the successful write) — the columns already defined by SPEC-v1 §2.1/S19 and already written by the Wave G importer, so Wave E's `extracted = fullContent != null` semantics (E22), Wave F's `fullContent ?: rawDescription` download preference (E23) and FTS/`fullLower` search coverage all activate for locally extracted articles with ZERO changes to those subsystems. `ReaderCacheHelper` (`cacheDir/readability/…`) is REMOVED: the disk cache is evictable (SPEC-v1 §1 D9 gap), invisible to Wave E/F/FTS, and has no `extractedAt`. One-time hygiene: on first coordinator init after upgrade, `cacheDir/readability` is deleted recursively (bounded, IO dispatcher; failure ignored — Android may evict it anyway). No DB backfill from cache files (they carry no timestamp; affected feeds re-extract under their existing contracts). `extractedAt` semantics: set to `now` on EVERY successful extraction write (first extract and re-extract); NULL iff `fullContent` IS NULL; never written independently of `fullContent`.

**E4 — Write path: one DAO method, one transaction, shadow + FTS included.** New `ArticleDao.applyExtraction(id, fullContent, fullLower, extractedAt)`: `UPDATE article SET fullContent = :fullContent, fullLower = :fullLower, extractedAt = :extractedAt WHERE id = :id`. `fullLower = TextNormalizer.normalize(fullContent)` computed by the caller in the same transaction (S11a write-path invariant); Room's `room_fts_content_sync_*` triggers carry the change into `article_fts` (S16 — extracted text becomes searchable; acceptance #12 "extracted-content changes results" now also covers LOCAL extraction). The write NEVER touches `rawDescription`, `shortDescription`, `originalContent`, `contentChangedAt`, `isUpdated`, `isUnread`, `isStarred`, `readAt`, `img`, `publishedAt`, `date` (S19), and does NOT bump `stateVersion` (the S18a choke point covers read/star/update state writers only; extraction is a content write like `applyWebUpdate`'s content fields, which bump `stateVersion` only when `markUpdated`). Because `rawDescription`/`shortDescription` are untouched, the flow list preview never changes on extraction → no Paging invalidation, no S25a generation churn (E22).

### Adaptive trigger & per-feed median

**E5 — Body text definition.** For ALL trigger/median/guard length computations, "body text" = `UpdateDetection.plainTextLength(article.rawDescription)` — the existing nh3-parity tag-strip (`UpdateDetection.kt:183–203`), the single canonical implementation (no second plain-text function). `rawDescription` is the Android analogue of web `content or summary` because ingest already stores `content ?: description` there (`RssHelper.buildArticleFromSyndEntry`, `RssHelper.kt:238–248`), so the web lesson "empty `content` alone is not a signal — many feeds put the full post in summary" is structurally satisfied: a feed whose full post lives in `<description>` has a full `rawDescription` and never triggers. Title, `shortDescription`, and `fullContent` are NOT trigger inputs.

**E6 — Adaptive trigger (exact formula, web parity).** An article is a TEASER candidate iff ALL of:
1. `article.link` is non-blank (web `if not entry["url"]: return False`);
2. `article.fullContent == null` (AUTO never re-extracts; re-extraction is MANUAL-only, E12 — documented deviation from web, where short extracted entries get silently re-extracted on every open; rationale: predictable mobile network use, and web's re-extract-on-open was a side effect of cleanup iteration, not a feature);
3. `len < 700` where `len = plainTextLength(rawDescription)` (web's absolute ceiling, `_can_fetch_full:517`);
4. `len < max(200, (0.4 × feed.medianBodyLength).toInt())` — web's exact expression incl. `int()` truncation toward zero (`_can_fetch_full:522–524`).
Empty/near-empty bodies are NOT special-cased (web parity): `len = 0` satisfies 3 and 4 via the 200-char floor, so genuinely empty entries are candidates — the guard that prevents garbage storage is E16, not the trigger. The trigger is evaluated at open time against the CURRENT row + its feed (E8); `medianBodyLength == 0` (unknown / all-empty feed) degrades exactly like web's `feed_median_body_len → 0`: threshold = `max(200, 0)` = 200.

**E7 — Per-feed median: durable column, recomputed at sync/import.** Add `feed.medianBodyLength INTEGER NOT NULL DEFAULT 0` (plain-text length estimate, chars). Room `version = 9` with `MIGRATION_8_9` = single `ALTER TABLE feed ADD COLUMN medianBodyLength INTEGER NOT NULL DEFAULT 0`; exported `app/schemas/…/9.json` committed; instrumented `Migration8To9Test` (schema match vs 9.json, existing rows preserved, `medianBodyLength == 0` after migrate). No SQL backfill: 0 means "unknown until the next recompute" and is safe by E6. Recompute rule (single implementation, `MedianBodyLength.recompute`): take the feed's most recent ≤100 articles with non-empty `rawDescription` (`ORDER BY rowid DESC LIMIT 100` via the `feedId` index; the cap bounds cost — web scans ALL entries server-side, which is unacceptable inside a mobile sync transaction), compute `plainTextLength(rawDescription)` per row, drop zeros, sort, return `lengths[size / 2]` (web's UPPER-median `lengths[len//2]`, `db.py:834–836`; 0 when no samples). Written via `FeedDao.updateMedianBodyLength(feedId, value)` immediately AFTER that feed's `storeEntries` transaction in `LocalRssService.sync` (inside the same per-feed `async` block; a crash between the two is harmless — the value is an estimate, recomputed every sync), and once per imported feed at the end of the Wave G importer's per-feed apply (samples from the imported rows). Deviation from web, recorded: web's median drifts upward after extraction (web extraction REPLACES `content` in place and the median scans it); Android's median is computed from `rawDescription`, which extraction never overwrites (S19), so the trigger baseline stays feed-supplied and stable. The median is an ESTIMATE input only — it is never displayed, never used for ranking, and a stale value degrades gracefully toward the 200-char floor.

### AUTO path

**E8 — AUTO timing: on open, never at sync.** The adaptive trigger fires ONLY when the user opens an article (web parity: `entry_page`/`open_entry`). No adaptive extraction at sync time for any feed: fetching pages for articles the user may never open burns metered data and battery for no observable gain, and web never did it. On open (`ArticleListReaderViewModel.renderContent`), evaluation order (binding): `fullContent != null` → render `FullContent(article.fullContent)` (no network); else `feed.isFullContent` → FORCE extraction (E9/E10; independent of the global toggle and the trigger); else global toggle ON (E20) AND trigger true (E6) → run AUTO extraction; else → `Description(rawDescription)`. AUTO extraction is NOT gated on network type or `account.syncOnlyOnWiFi` (recorded decision: one page fetch per opened teaser article is the same data the user would spend tapping "View original"; the global toggle is the off switch; flagged-feed PREFETCH keeps its existing ungated contract, E9).

**E9 — `feed.isFullContent` and ReaderWorker: KEEP the contract, FOLD IN the pipeline.** The per-feed "Parse full content" flag (`Feed.kt:40`, feed/group toggles verified in §1) keeps its existing meaning: FORCE-extract this feed's unread articles at sync time, unconditionally (no teaser trigger — the user explicitly asked for it; this is also the de-facto per-feed "always extract" override). What changes: (a) `ReaderWorker` calls `ExtractCoordinator.extract(…, PREFETCH)` instead of `ReaderCacheHelper.checkOrFetchFullContent`; (b) `queryUnreadFullContentArticles` gains `AND a.fullContent IS NULL` (DB truth replaces cache-file existence as the skip condition — already-extracted unread articles are never re-fetched at sync); (c) per-article extraction failures NO LONGER produce `Result.retry()` — PREFETCH is best-effort (E21); the worker returns `Result.success()` unless the worker itself fails structurally (rationale: today one dead link retries the ENTIRE prefetch chain forever, re-fetching every other article on each attempt); (d) `Semaphore(2)` prefetch concurrency is preserved (SPEC-v1 §12 "2 extractions"). The post-sync chain (`SyncWorker.enqueuePostSyncChain`) is otherwise unchanged. `SyncWorker.doWork`'s `deleteCacheFor` loop is deleted along with the cache (E3).

**E10 — AUTO render/fallback contract.** When the trigger fires on open: the reader enters the existing `Loading` state (the `Content.kt:118` indicator) while the coordinator runs under the E18 timeouts; success → `FullContent` (in-place state update, no list invalidation, E4); ANY failure (network, guard, challenge, unproductive, timeout) → `Description(rawDescription)` — the feed content the user would have seen anyway. `ReaderState.Error` is REMOVED from the extraction path (the current error wall at `ArticleListReaderViewModel.kt:562–566` is deleted; if `Error` has no remaining producer it is deleted from the sealed interface — verified at implementation time). For `feed.isFullContent` feeds the open-time behavior is the same state machine with the trigger bypassed (force), replacing today's cache-read-then-fetch (`renderContent:531–543`).

### MANUAL path

**E11 — MANUAL extract: existing BottomBar article button, extended semantics.** The icon-only BottomBar button (`BottomBar.kt:145–162`, 48.dp target, haptic, `Icons.AutoMirrored.*.Article`) keeps its position and grammar. Semantics: `fullContent == null` → tap runs MANUAL extraction (any article, any feed, regardless of trigger — web's always-available manual extract); busy → button disabled + `Loading` indicator per E10; success → `FullContent`; failure → stays on `Description` + transient signal (E13). `fullContent != null` → tap TOGGLES the rendered view between `FullContent` and `Description` (existing behavior). The toggle is deliberately KEPT (deviation from web, which has no toggle because extraction replaces content in place): Android stores both bodies side by side, the toggle is the user's escape hatch from a bad extraction, and the S22 diff pane is only reachable on the `Description` path (`ReadingPage.kt:414–421`) — removing the toggle would strand "View changes" for every extracted article (Wave E interaction, E22).

**E12 — MANUAL re-extract: TopBar action, extracted-only.** Re-extraction is an explicit TopBar icon action (fourth `FeedbackIconButton` after Palette/Share/Download, icon-only per the toolbar grammar, `contentDescription` "Re-extract full article", ≥48.dp semantics via the existing button component), VISIBLE/ENABLED only when `article.fullContent != null`. Re-extract semantics (web `_run_extraction` on `extracted=1`): the result MAY be shorter than the stored extraction (cleanup improvements) and replaces it when it passes the re-extract guard (`> 120` plain-text chars, E16); on success the rendered `FullContent` view updates in place (if the user is viewing `Description`, only the stored row updates — no forced view switch); on failure the stored extraction is untouched. Busy state mirrors the S27a download icon pattern: in-flight icon (e.g. `Icons.Outlined.Sync`/progress tint), disabled while running. Rationale for a separate control instead of web's single button: on Android a single tap-to-re-extract would destroy the view toggle (E11), and accidental re-extracts would spend a network fetch per tap.

**E13 — Busy/failed UX: quiet, no error wall (binding).** No dialog, no snackbar-with-action, no full-screen error, no persistent badge for extraction failures. Busy = existing `Loading` indicator (AUTO/MANUAL-from-description) or in-flight icon tint (re-extract while content stays rendered). Failure = silent fallback (E10/E11/E12) plus ONE transient signal satisfying S19's "transient 'extraction unavailable' state on the article only": the BottomBar/TopBar extraction icon briefly (≤3 s) shows a disabled/outline "unavailable" tint with the existing `contentDescription` unchanged — implemented as ephemeral UI state, never persisted, never a toast on AUTO (AUTO failures are fully silent: the user sees feed content and no state change, exactly like web). TalkBack: the transient state must not steal focus; icon states keep stable contentDescriptions.

### Extraction pipeline internals

**E14 — Readability4J stays the extractor.** `Readability.parseToElement(html, link)` (Readability4JExtended 1.0.8 + `RYArticleGrabberExtended`) remains the container-picker/scorer. It already covers (verified against the 1.0.8 patterns, §1): script/style removal, unlikely-candidate stripping (nav/menu/sidebar/social/share/sponsor/comment/footer-ish/pagination/popup/ad-break…), byline removal, empty header/h1–h6 removal, div→p normalization, best-candidate selection (analogue of web's largest-`main`/`article` pick). It does NOT cover: title headings with site suffixes (Android today matches EXACT h1 text only, `RssHelper.kt:190–193`), YAML frontmatter, TOC chrome (`toc-*`, `table-of-contents` are absent from every 1.0.8 pattern), page-level `<time class="date">`. The web's whole-page fallback container pick is NOT ported: readability4j always returns article content or null (null → failure, E21).

**E15 — Deterministic post-cleaner (`ExtractCleaner`), ported web rules.** New pure-Kotlin/jsoup pass `infrastructure/html/ExtractCleaner.kt` applied to the Readability output BEFORE the length guard, in this order (ports of the 2026-11-14 Wolfram-writings lessons):
1. **Title dedupe (replaces the exact-h1 removal in `RssHelper`):** drop the FIRST `h1` or `h2` whose normalized text matches the entry title — normalization = strip tags, `lowercase(Locale.ROOT)`, replace every non-`[\w\s]` run with a space, collapse whitespace (port of `_norm_title`, `extract.py:193–196`); match = equality OR the site-suffix prefix rule `longer.startsWith(shorter) && shorter.length >= 0.6 * longer.length` (port of `_drop_duplicate_title:214–215`). Only the first matching heading is removed; headingless or non-matching output is untouched.
2. **YAML frontmatter:** drop `<p>` blocks whose stripped text matches `^\s*-{3,}\s*(title|description|canonical_url|date|author|slug|tags|categories|layout|permalink|id)\s*:` (case-insensitive; port of `_FRONTMATTER_KEY:169–173`, `_strip_frontmatter:178–190`).
3. **TOC chrome:** remove elements whose `class`/`id` contains token `toc-` or `table-of-contents` (port of the two JUNK_HINTS `extract.py:30` that readability4j lacks; substring match on the attribute values, mirroring web's `hint in merged`).
4. **Page-level dateline:** remove `<time>` elements whose `class` attribute contains any EXACT whitespace-split token in `{date, post-date, entry-date, published, updated}` (port of `_is_junk:85–92`; inline prose `<time>` without those classes is kept).
Web rules NOT ported, with reasons (binding — do not "fix" these in review): `<head>`/`<title>` subtree dropping and html/body unwrapping are structurally impossible in the jsoup/Readability output (article content is a body-subtree fragment; the web rule exists because nh3 keeps disallowed tags' TEXT and the web cleaner is regex-based); void-tag stack safety is N/A for a DOM parser (research correction C3). Fixtures for all four rules ship as JVM unit tests with synthetic HTML only (D16), including a Wolfram-style frontmatter fixture and a title-suffix fixture ("Article Title — SiteName").

**E16 — Quality guards (exact rules).** Applied in pipeline order:
1. **Challenge/bot-wall rejection (S19 retained):** `DownloadHtmlSanitizer.isChallenge(documentHead)` on the fetched document's head (existing Wave F implementation, markers verified `:74–81`) → failure `challenge`. Additionally (S19 productive-ratio guard): if `plainTextLength(cleaned) × 20 < rawHtml.length` (< 5% productive text) → failure `unproductive`.
2. **Length guard (web-exact; AMENDS S19's wording — see E26):** let `resultLen = plainTextLength(sanitizedCleaned)`. For AUTO/MANUAL/PREFETCH of a NOT-yet-extracted article: accept iff `resultLen > max(plainTextLength(rawDescription), 120)` (web `min_len = max(current_len, 120)`, strict `>` per `_run_extraction:582–584`). For RE_EXTRACT of an already-extracted article: accept iff `resultLen > 120` (web `min_len = 120`; a SHORTER-than-before clean result is acceptable — junk removal may legitimately shrink it). Rejected results write NOTHING (prior content untouched, no `extractedAt`, D6: a failed extraction never claims success). SPEC-v1 S19's "≥ 200 chars OR ≥ 40% of median" acceptance rule is SUPERSEDED: those constants are the TRIGGER (E6), not the result guard; keeping them as a result guard would double-apply the median and reject legitimate extractions of short-but-complete articles (web never did this).
3. **Stored-size cap:** sanitized result > `DownloadPolicy.TEXT_MAX_BYTES` (2 MiB) → failure `oversize` (never truncate HTML; DB-bloat guard, value reused not re-decided).
4. `extract_article`'s <120 floor (`extract.py:240–241`) is NOT separately ported: guard 2 subsumes it for every mode (`max(x,120) ≥ 120`, strict `>`).

**E17 — Fetch safety: public-IP + redirect guard (web `require_public_url` parity).** New `infrastructure/net/SsrfGuard.kt` (pure, JVM-unit-testable): (a) URL scheme ∈ {http, https}; (b) host present; (c) NO userinfo (`username`/`password` rejected — web `safe_web_url:223–224`); (d) port valid (≤ 65535, `ValueError` parity); (e) resolve host (injectable `okhttp3.Dns` seam; literal IPs accepted directly) — EVERY resolved address must be "global", rejecting: loopback, any-site-local/private (10/8, 172.16/12, 192.168/16), link-local (169.254/16, fe80::), unspecified, multicast, IPv6 unique-local (fc00::/7), IPv4-mapped IPv6 whose mapped address is non-global, carrier-grade NAT 100.64.0.0/10, 192.0.0.0/24, 198.18.0.0/15, 198.51.100.0/24, 203.0.113.0/24, 240.0.0.0/4, 255.255.255.255 (the `ipaddress.ip_address.is_global` set, CPython 3.13 semantics — pinned by a unit-test table). Resolution failure → reject. Redirects: the extraction client sets `followRedirects(false)`/`followSslRedirects(false)` and the coordinator follows manually, max 5 hops, running the FULL guard on every hop URL (web's httpx client does not silently follow into private ranges either); hop-limit exceeded → failure. Residual risk, recorded honestly: DNS-rebinding TOCTOU between guard resolution and OkHttp's own resolution exists in the web design too (getaddrinfo then re-resolve); accepted at parity, mitigated per-hop. The guard applies to extraction fetches ONLY (article links); feed fetching keeps its existing behavior (out of scope).

**E18 — Extraction HTTP client, timeouts, UA.** New `@ExtractHttpClient` provided in `OkHttpClientModule` (mirrors the `@DownloadHttpClient` pattern `:83–96`): built from `cachingHttpClient(cacheDirectory = null, connectTimeoutSecs = 15, readTimeoutSecs = 30)` + `.callTimeout(60, SECONDS)` + `.followRedirects(false).followSslRedirects(false)` + the EXISTING `UserAgentInterceptor` (UA unchanged — E1). Connect/read values match the S28 "feed/extraction client pinned to the same connect/read values" row; the 60 s call cap bounds a single page fetch (vs 120 s for image downloads). Response body read is capped at 5 MiB (streaming byte-count limit; exceeded → close + failure `oversize`; rationale: page HTML headroom above the 2 MiB stored-text cap, hard bound against hostile multi-GB responses on metered links). Charset detection: reuse the existing header+meta logic (extract it from `RssHelper.parseFullContent:155–186` into the coordinator's fetch step — behavior preserved). The pre-existing `trustAllCerts = true` posture of `cachingHttpClient` is inherited unchanged and explicitly OUT of scope for this upgrade (it is the app-wide feed-fetch posture; changing it is a separate security decision — recorded here so review does not silently "fix" it inside this wave).

**E19 — Sanitize before store.** The cleaned extraction passes `DownloadHtmlSanitizer.sanitize` (the S30a write-time sanitizer already used by downloads and the Wave G importer — one sanitizer for all stored HTML) BEFORE the length guard measurement and BEFORE the `applyExtraction` write. The render path is unchanged (it renders stored, already-sanitized HTML).

### Settings & failure model

**E20 — Settings: global toggle default ON; per-feed override DEFERRED.** New `AutoExtractPreference` (DataStore boolean, sealed ON/OFF class following `MarkReadOnOpenPreference.kt` exactly — key `autoExtractFullContent`, default **ON**, wired into `Settings`/`SettingsProvider` + `LocalAutoExtractFullContent` composition local). UI: `SettingItem` + `RYSwitch` in `InteractionPage`'s existing `reading_page` section (`InteractionPage.kt:192+`), title "Auto-extract full articles", desc reusing `R.string.parse_full_content_desc` ("Fetch full articles from webpages") — matching the `hide_empty_groups` row pattern (`:129–138`). Semantics: gates the ADAPTIVE on-open path (E8) only; it does NOT gate `feed.isFullContent` PREFETCH/force behavior (E9) and does NOT gate MANUAL extract/re-extract (explicit user intent, web parity: the manual icon always works). This AMENDS SPEC-v1 §12's "auto full-text extraction (global): OFF for new installs" row (E26) per the card's product decision; the §12 rationale ("avoid porting a hidden network-on-open default") is addressed by: the fetch is one page per opened teaser article, visibly loading, with a first-run-visible toggle at default ON exactly like web `auto_fetch_full`. Per-feed adaptive opt-out (a "no auto-extract" chip for linklog-style feeds whose short posts are complete) is DEFERRED to a later card: the global toggle + the E11 view toggle bound the damage today, and the per-feed surface needs a tri-state design (force/adaptive/off) that this wave must not pre-decide. Known accepted risk (recorded, web-identical): for linklog-style feeds, AUTO extraction of a <200-char post may replace the view with the LINKED page's article; mitigation = one tap on the BottomBar toggle shows the original feed content; the deferred per-feed opt-out is the durable fix.

**E21 — Failure model: silent no-op everywhere (binding).** Every failure (blank link, SSRF reject, DNS failure, connect/read/call timeout, non-2xx, >5 redirects, oversize response, challenge wall, null Readability result, cleaner exception, length-guard reject, oversize result, DB write error) produces: NO DB write, NO crash, NO dialog, NO persistent state. Per-mode observable: AUTO → `Description` fallback (E10), fully silent; MANUAL → stay on current view + ≤3 s transient icon state (E13); RE_EXTRACT → stored extraction untouched + transient icon state; PREFETCH → per-article skip, worker continues, no `Result.retry()` (E9). Failures are logged via Timber (`RLog`/existing tag convention) for diagnosis only. This replaces the current `ReaderState.Error` wall (correction C2). Extraction failures never affect sync results, unread counts, or download states.
